# A/B 实测：v0.1.0 vs v0.7.3

- 日期：2026-10-21
- 版本：v0.1.0（worktree `dsh-artex-v0.1`） vs v0.7.3
- 环境：同一台 Windows 主机、同一 DSH profile、模型 deepseek-flash、只读任务
- 方法：两版各跑同一组 2 个任务 × 2 次（n=2/任务，共 4 次/版）；相同参数：
  `max_workers=1`、`max_rounds=2`、`max_stalls=2`、`budget_ms=150000`、`worker_timeout_ms=120000`、`planner_timeout_ms=90000`、`settle_grace_ms=40000`、`heartbeat_ms=60000`、`debounce_ms=300`
- 任务：
  - **A（SMB）**：确认本机 SMB 服务端共享数量与清单（或负证据）
  - **B（LISTEN）**：统计本机 LISTEN TCP 端口总数与证据
- token 口径：v0.7.3 直接取任务 `usage`；v0.1.0 无 usage 字段，从 DSH session 日志按任务窗口聚合子会话 `assistant/message.usage`。聚合脚本 `bench/measure-task-tokens.mjs` 在 v0.7.3 任务上与任务 usage **逐字段一致**（calls/input/output 全等），因此跨版口径可比。

## 分析

### 1. 完成度是最大差异

v0.1 的四次里只有 A2 完成：A1 有 3 条事实、1 个发现，结论正确（共享数量已确认）却因 2 轮用尽停在 `max_rounds`；B1/B2 都已用 3 个独立来源确认同一端口集合，仍在预算内 `timeout`，目标未证明。

v0.7.3 四次全部完成：同样是 2 轮上限，首轮拿到充分证据后 planner 直接 `prove_goal`，未领取的意图标记 `stopped/goal_met`，没有遗留 `open` 意图。

### 2. token 下降主要来自"少调用、少过度探索"

v0.7.3 平均调用 12 vs 21.5（-44%），平均输出 5,995 vs 19,928（-70%）。单次调用输入只差 1.8%，说明**提示词投影不是本轮主因**；主因是：

- v0.1 倾向于多派交叉验证意图、worker 写更多 finding（B1 3 个、39 步），但没有收官机会；
- v0.7.3 在首个充分突破后停止追加，事实/发现各 1 条即可证明，避免重复取证。

### 3. 证据少不等于质量差

v0.1 平均事实/发现更多（2.5/1.75），但其中 3/4 的任务没有把证据转成目标证明；B1 甚至已有 3 个独立来源仍超时。v0.7.3 的 1 fact + 1 finding 覆盖了"命令 + 输出 + 交叉核对"，并以 brief 明确口径（端点总数 vs 唯一端口数），可复核性没有下降。

### 4. 时间

平均用时从 133.5s 降到 42.75s（-68%），主要因为不重复探索、不需要等满预算。v0.1 的 3 次失败都跑到 123–165s，属于"花了钱没收官"。

### 5. 与历史 A/B 的差异

2026-10-20 的 v0.1 vs v0.3.2 结论是"v0.3.2 完成率更高但 token +20.8%"，因为当时用 audit 模式且 v0.3.2 过度验证（B2 40.2k）。本轮改用 objective + 明确单目标 + `max_rounds=2`，v0.7.3 的"充分即停"策略生效，因此成本方向反转为 -57%。两个结论并不矛盾：**模式与 goal 边界决定探索深度，版本只决定单次成本与收官可靠性**。

## 局限

- n=2/任务（4 次/版），方差仍大；B 任务两次采样间隔数分钟，端口数可能变化，但两版都读到同一端口集合。
- v0.1 的 token 来自日志聚合，不是插件内建 usage；已用 v0.7.3 的 4 个任务做逐字段校验（calls/input/output 全等），但日志保留策略变化会影响未来复跑。
- 版本差异不只是提示词：v0.7.3 还修复了收官/证明轮、事件唤醒、状态机、成本上限等；不能把全部差异归因于 prompt。
- 未覆盖 audit 模式、多 worker、objective 多路径回溯；这些需要单独 A/B。

## 结论

| 维度 | 结论 |
|---|---|
| 完成度 | v0.7.3 **4/4** vs v0.1 **1/4**；v0.1 的失败模式是"证据已够但不判目标/预算耗尽" |
| 成本 | 平均总 token **-57.3%**（40,770 → 17,421），每个完成任务成本 **-36.0%** |
| 延迟 | 平均用时 **-68.0%** |
| 证据 | v0.1 写得更多但常无法收官；v0.7.3 用更少事实完成可复核证明 |
| 归因 | 主要来自调用次数/过度探索下降（-44% 调用、-70% 输出），不是单次提示词变小 |
| 建议 | 长任务仍应关注 audit 模式的过度验证；objective 单目标下 `max_rounds=2` 已足够体现 v0.7.3 的收官优势 |

## 复现

```bash
# v0.1 worktree
git worktree add ../dsh-artex-v0.1 baseline/v0.1
# 安装对应版本后，用上面的任务与参数运行
node bench/measure-task-tokens.mjs <taskId> <parentSessionLog> <sessionsDir>
```

测量脚本要求 PATH 中有 `zstd`（支持 multi-frame）；只读 session 日志，不改任务快照。
